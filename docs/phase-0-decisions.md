## D1 — Identifiers

Requirements §2.1 names the identifiers. This sets their shape.

| ID | Generated by | Natural key (unique per tenant) | Source in telemetry |
|---|---|---|---|
| `PlatformTenantId` | install | `key`: slug `^[a-z0-9][a-z0-9-]{1,62}$`, immutable | Collector stamps the slug as `juice.platform_tenant_id` |
| `EnvironmentId` | platform | normalized `deployment.environment.name` | resource attribute; missing → environment `unspecified` (kept, not dropped) |
| `ServiceId` | platform | `service.namespace` + `service.name` (namespace may be empty) | resource attributes |
| `InstanceId` | platform | `service.instance.id` | resource attribute; missing → derived from `host.name` + `process.pid`, marked low confidence |
| `ResourceId` | platform | type + canonical key (D3) | resource attributes and host metrics |
| `ApplicationId` | platform | configured mapping from services (D3), default one application per `service.namespace` | none directly |

- Every platform ID is a UUIDv7 created by the platform. Telemetry values are only natural keys, never IDs (§2.1).
- **A service is environment-independent.** `orders` in staging and production is one service; health and instances
  are per service × environment. Dashboards and alerts filter by environment.
- The tenant record holds the slug; startup checks `JUICE_PLATFORM_TENANT_ID` against it (§4 step 6).
- The .NET SDK gives each process a random `service.instance.id` unless the host sets one, so a restart is a new
  instance. That is the intended model: instances are ephemeral, services are not.

## D2 — Application tenant attribute

Juice puts no tenant on telemetry today. When a Juice host wants to report the business tenant, it needs a name that
the Collector does not delete.

- **Recommend** `juice.application_tenant_id`, as a resource attribute for a single-tenant host or a record attribute
  for a shared one. It is descriptive context (§2.1), never used for authorization, storage routing or the platform
  tenant.
- The Collector strip list (`juice.platform_tenant_id`, `platform.tenant.id`, `tenant.id`) does not touch it. Do not
  use `tenant.id`, which is stripped.
- Adding it to Juice (for example from `MessageContext` or the multi-tenant resolver) is separate framework work, not
  needed for the MVP.

## D3 — Resource identity and reconciliation

| Resource type | Canonical key | Notes |
|---|---|---|
| host | `host.id`, else `host.name` | host metrics carry `host.name` from the Collector's detector |
| container | `container.id` | linked to its host and instances when attributes allow |
| k8s pod / workload | `k8s.pod.uid`; workload: namespace + kind + name | Phase 1 records them, rollups come later |
| messaging destination | `messaging.system` + `messaging.destination.name` | from producer and consumer spans |
| database | `db.system.name` + `server.address` + `db.namespace` | from client spans |

- **Reconciliation.** Each run reads distinct resource attribute sets since its checkpoint, bounded by time and row
  limits, using `platform_reader`. It normalizes values (trim, lowercase keys, length and count limits) and upserts by
  natural key with first-seen and last-seen times.
- **Renames.** Handled by aliases in deployment config (old key → service), never by guessing.
- **Absence.** An instance is inactive after 15 minutes without telemetry. Services and resources are never deleted
  automatically; they become `Offline` through health (D4). Inactive instances are pruned after 30 days.
- **Dependencies.** Inferred from client/producer → server/consumer span pairs. Each keeps its evidence (span counts,
  first and last seen) and a confidence: `observed` when both sides are seen, `inferred` from one side only. A
  dependency is never stated as certain.
- **Limits.** At most 64 attributes per resource and 256 characters per value. Anything beyond is truncated and
  counted, never indexed.

## D4 — Health defaults

Approve §7 as written, with these starting numbers (per resource type, configurable):

| Setting | Default |
|---|---|
| Evaluation interval | 30 s (the §9 target) |
| Freshness grace | 5 min. Juice hosts export metrics every 60 s by default, so this is five missed exports |
| Minimum samples per window | 3 |
| Unhealthy instance quorum | ≥ 50 % of active instances unhealthy → service `Unhealthy`; any unhealthy → `Degraded` |
| Error-rate thresholds | `Degraded` ≥ 1 %, `Unhealthy` ≥ 5 %, over server and consumer spans in 5 min |
| Rollup | application = weighted children; optional children don't count; no "worst child wins" |

## D5 — Rule model

MVP rules are typed templates over ClickHouse (§8), loaded from `rules.json` in deployment config. Each rule has: scope
(service, environment, resource), schedule (1 min), threshold, `forDuration`, recovery threshold and duration,
cooldown and severity.

| Template | Reads |
|---|---|
| `error_rate` | server/consumer spans with `StatusCode = 'Error'` / all |
| `latency_p95` | span duration per operation |
| `throughput_absent` | no server/consumer spans for a service that had them |
| `mediator_errors` | `juice.mediator.errors` increase |
| `consumer_failures` | `juice.messaging.consumed` with `juice.dispatch.result = failure` |
| `delivery_failures` | `delivery_failure_total` / `delivery_attempt_total` |
| `host_resource` | CPU utilization, memory used, filesystem used % |

Missing data evaluates to "no data", never zero (§8).

## D6 — OTLP authentication in production

| Option | For | Against |
|---|---|---|
| **Static bearer tokens over TLS (recommended)** | Built and tested locally. One token per client in a mounted secret file, so revoking one client doesn't affect the others. Works with every OTel SDK through `OTEL_EXPORTER_OTLP_HEADERS`. | Long-lived secrets; rotation is manual (add new, roll clients, remove old) |
| OIDC client credentials | Short-lived tokens, central identity | The OpenTelemetry .NET exporter sends static headers only. Every host would need a token-refreshing handler or a local Collector agent. |
| mTLS client certificates | Strong identity, no shared secret | Certificate issuance and rotation per host. Standard extensions expose no `auth.*` identity from the certificate. |

- **Recommend static tokens** for the single-tenant MVP: the tenant is static, so client identity only gates access
  and selects nothing.
- Rotation runbook: add the new token line and restart the Collector, roll the clients, then remove the old line and
  restart again. Tested on the local stack (2026-11-01): a new token is refused until the Collector restarts, and a
  removed token is refused after it. The token file is a single-file bind mount; whether a directory mount picks up
  changes without a restart was not tested.
- **Revisit for shared SaaS** (§2.2), where identity must map to a tenant: OIDC through a Collector agent, or mTLS.

## D7 — Targets, data classification, retention

- **Targets.** Approve §9 as written. Measured so far: ingestion freshness p95 1.36 s in a 60 s reference-rate run
  (`deploy/local` README). The 30-minute run belongs to Phase 4.
- **Classification.**

  | Class | Contents | Handling |
  |---|---|---|
  | Restricted | Business payloads, credentials | Never ingested. The Juice log processor drops payloads; the Collector deletes credential-like attributes |
  | Confidential | Application log messages, exception messages, URLs, user and tenant ids that apps choose to log | Stored with retention; application owners keep personal data out of log messages |
  | Internal | Span names, metric values, resource attributes | Stored with retention |

- **Retention.** Traces and logs 30 days, metrics 90 days (the §9 reference profile, already the `deploy/local`
  default). Each deployment validates these against its disk budget.

## D8 — Console and external visualization integration

Replaces "Versions and Grafana isolation" (approved earlier on 2026-11-01). The direction is in
[the UI architecture](juice-observability-ui-architecture.md).

- **Juice Console is the primary and default UI**, built with Angular and `juice-layout`, and part of the MVP. It
  reads everything through the Juice API, including traces, logs and metrics, and never reads ClickHouse directly.
- **Grafana is optional**, for customers who already run it. A deployment without Grafana is complete. The API carries
  no Grafana-specific fields; Grafana appears only as an optional integration link.
- **When Grafana is used:** read-only, bounded ClickHouse credentials, and its own sign-in. Juice authorization never
  depends on it.
- **Versions** pinned and tested in `deploy/local`: Collector contrib 0.163.1, ClickHouse 26.8.36.3, PostgreSQL 17.10,
  Keycloak 26.7.5; optional Grafana 13.2.5 with ClickHouse plugin 4.22.1.
